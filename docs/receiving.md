# Receiving

The receiving screen posts a quantity into a bin. The top of the form is the receipt header. The line under it is a search, an optional SKU, one bin, a quantity, and a comment. The SKU can be chosen now or linked later. A line saved without a SKU does not move stock.

## Header

| Label | Stored as | Notes |
| --- | --- | --- |
| Project | `stock_events.project` and, when a cycle opens, `bin_cycles.project` | A combobox. Focusing it lists this person's 10 most recently used projects from receipts with their initials, newest first. Typing narrows that list. A name that is not listed is still stored as typed. |
| Receiving date | `stock_events.received_on` | Defaults to today in America/Los_Angeles. |
| Incoming bin | `stock_events.incoming_tag` and, when a cycle opens, `bin_cycles.incoming_tag` | The database column is still `incoming_tag`. |
| Originating system | `stock_events.origin_description` and, when a cycle opens, `bin_cycles.origin_description` | A combobox, like Project. Focusing it lists originating systems already stored on receipts, newest first. Typing narrows that list. A name that is not listed is still stored as typed, and the next receipt offers it. Older receipts keep the text already stored. The database column is still `origin_description`. There is no separate system table. |
| Orig. system qty | `stock_events.origin_qty` | Optional whole number. The field label is shortened so the header stays on one row. This is the quantity the originating system reports, not the quantity put in the bin. |
| Purchase order | `stock_events.purchase_order_id` | Optional. Typing a number lists matching purchase orders. Choosing one stores that order and its vendor. |
| Vendor | `stock_events.vendor_id`, and `bin_cycles.vendor_id` when this receipt opens the cycle | Required when the purchase order is empty. The receipt is then consigned (`ownership = consigned`) on the receipt and on stock units created from it. A purchase order fills the vendor from the order and does not set consigned. |

A bin that already holds stock keeps the cycle it opened with. The receipt line still stores the header that was on the form. A receipt with no purchase order cannot be saved until a vendor is chosen, and that vendor stays on the receipt for later accounting and returns.

The project field is filled when the page opens. This browser keeps the last value for this person in `localStorage`, including a cleared field. The first visit on a device, or a browser that blocks storage, uses the project on that person's latest receipt. Clear empties the field. The incoming bin, originating system, receiving date, and originating quantity stay as they are. After a save, that whole header stays filled.

## Receiving date before go-live

`RECEIVING_DATE_EDITABLE` in `lib/receivingSettings.ts` is the only switch. It is `true` for now, so the date is a date input and the chosen day is stored. Set it to `false` after go-live. The input becomes today's date, and the server stores today even if the browser sends another day.

## Line

Serials and country of origin are optional, under the line. A quantity of 1 to 8 gives each piece a serial and a country. Above that, serials are one per line, and a line may name a country after a comma (`SN-2, CHN`). The country box applies to every line that does not name one. Pasting a spreadsheet column or row into a serial field splits the same way a pick does: newlines and tabs are separate serials, and blank cells are dropped. A paste of more than one serial sets the quantity to that count and replaces the serial list. One serial stays in the field and does not change a quantity that is already filled in. Typing a quantity after the paste still wins: more serials than pieces is refused, and fewer serials leaves the rest as quantity only. Save creates one stock unit per serial on that item and bin. A serial already recorded for the item is refused in a sentence.

The line is one row: a short search, the SKU, the name, the quantity, the bin, then Cleaned or Wiped when the taxonomy asks for it, then the comment. A title lines up with the text in its box, not the box edge. Left-aligned titles share the left edge of that text. Qty is right-aligned, so the last digit lines up with the last letter of the title. The quantity starts blank. Saving with it empty says the quantity is missing, and a blank field is not stored as 0 or 1. When Orig. system qty is a whole number greater than 0 and the line quantity is not an integer multiple of that number, a yellow warning sits under the line, beside Qty, and on the saved receipt. The line still saves. A blank or zero system qty skips that check. Save receipt is the save icon at the end of that row. Its tooltip is Save receipt. One click posts the line, including when the cursor is still in the bin field. That click is not spent looking the bin up. On a phone the fields stack. The header fields stack the same way.

Search uses the same token order as before. Choosing a result leaves that typed text in Search. A search that comes back with one item selects that item, the same as choosing it. Choosing any row moves the cursor to Qty, including a row picked from a longer list. The SKU beside Search starts as the chosen item. That field can be typed over. An exact SKU replaces the item, and the name updates to that item. Search keeps the text that was typed, and that text is what is stored. The name is that item's name, as text, not a field. The description sits under the name, with room below the line so it stays clear of the card border. The name column is wider than the comment so more of that description fits.

The comment is only the text the clerk types. It does not start with `cleaned`, `dirty`, `Wiped`, or `Pending Wipe`. A CPU taxonomy shows Cleaned between the bin and the comment, unchecked. An HDD or SSD taxonomy shows Wiped in that same place, unchecked. Memory and the other taxonomies show neither box. With no item selected, the taxonomy is unknown, so neither box is shown and both flags stay empty. The title sits on the same line as the other field labels, and the box sits in the same band as the quantity, bin, and comment inputs. The taxonomy is the item's short code, long code, or taxonomy name: `CPU` or `CPU/…` is a processor, and `HDD`, `SSD`, `DSK/HDD`, or `DSK/SSD` is a drive. Checking the box stores true. Leaving it stores false. The other flag stays empty. A blank comment still takes a multi-token scan, and that scan is stored as written.

The bin is one code field. It starts blank. One note under the line gives the on-hand total for this SKU in the bin typed there, and only when an item is selected: `96 PCS of this SKU are already in this bin at HWS.00.00.00.` Several receipts into that bin add up to that one total. No item means no note. The note is also hidden when that total is 0 and no other open bin on this project holds the SKU. When other bins do, the same note continues `More in other bins: 10010-C (x48), 10069-C (x48).` Choosing one of those bins fills the field. The line does not also print the bin code, its location, the open cycle, the project, or the originating system. Choosing a SKU fills the field with the bin from the most recent receipt of that item, on any project, when the clerk has not typed a bin. No receipt for that item leaves the field blank. The field does not show the next counter number. A code that already exists and can take stock is accepted. A bin with quantity and no open cycle is refused. A code that is not in the warehouse asks whether to create it. Yes calls `create_receiving_bin` with that code, and the suffix `-B`, `-C`, or `-P` is the type. An empty bin on save asks for one and suggests the next number from the shared counter, as a box (`20000-B` and onward). That suggestion is only in the prompt. Box, Crate, and Pallet on that prompt keep the same number and change the suffix. Yes creates that bin. The counter still lives in Settings. A line with no SKU still uses that same bin. The code has to be a real warehouse bin. Nothing is written to `bin_contents`, and no cycle quantity changes, until an item is linked.

A typed code that ends in `-B`, `-C`, or `-P` is that type. The database still says `Code 10099-C is a crate, but Box is selected` if an older client sends the wrong type.

A number already stored under another suffix is not offered for create. Typing `10042-B` when `10042-C` is on file says BIN 10042 is a Crate and you selected a Box, please adjust your bin selection, and offers Use Crate `10042-C`. That puts the crate on the line. It does not insert another row for 10042. If the database still refuses the create, the form shows that sentence. Production does not replace it with the Server Components digest.

The receipt stores the signed-in person's two initials. With sign-in off, that value is `OP`. Saving does not change `items.quantity`. The button stays disabled while that click is saving. The click sends one `client_request_id`. A second click during the save is ignored, and a repeat of the same id returns the line already written instead of inserting another. After a save, the header stays filled, the line fields clear, and the cursor returns to Search. The success note and print buttons sit in the page above the line. An empty bin reads `Put Away 4Pcs SKU94415 into EMPTY bin 10059-C`. A bin that already had stock reads `Added 4Pcs SKU94415 into bin 10059-C`. A line saved with a search and no SKU reads `Saved 4 pcs of "samsung 860" into bin 10059-C (pending item)`. That note is not the Put Away wording. Print item label is hidden on that note, because there is no SKU yet. The receipt is the first row in Recent entries for that project.

Save still requires the search text, the item quantity, and a bin when the SKU is empty. The comment follows the same rule as a line that has a SKU: it can be blank. SKU and name stay empty. The exact typed search is stored on `stock_events.search_query`. Cleaned and Wiped stay null. The row is still a `receive_into_bin` event, with `item_id` and `cycle_id` null. It does not invent a placeholder SKU.

## Recent entries

The table lists `receive_into_bin` rows for the project in the header, newest `received_on` first, then the time the row was written. Each page is 50 rows. First page, Previous page, Next page, and Last page move through the older receipts. First page and Previous page are disabled on page 1. Next page and Last page are disabled on the last page, and while that page is loading.

Columns follow the receipt, in this order: Date, Initials, Project, Incoming bin, System, System Qty, Search, SKU, Item name, Item Qty, Putaway, Comment. Putaway is the destination bin and the location stored on the receipt (`to_location_id`), for example `20042-B · HWS.00.00.00`. Each receipt is one table row with those twelve cells. The desktop headers read Date, Init., Project, Incoming bin, System, System Qty, Search, SKU, Item name, Item Qty, Putaway, and Comment, and a header wraps only between words. The body is 13px Plus Jakarta Sans with tabular numbers, and the cells use about 6px of horizontal padding. Date, initials, project, incoming bin, SKU, system qty, and item qty stay on one line and take the width of their text. System stays on one line and is at least 12 characters wide. Search stays on one line, is at least 12 characters wide, and ellipsizes. The full search text is the cell title. Item name is at least 60 characters wide and ellipsizes after that. Comment uses the width that is left, at least 16 characters, and ellipsizes. The full item name and comment are the cell titles. When those columns do not fit, the table scrolls sideways and the item name stays at least 60 characters wide. Item Qty is right-aligned. Initials are the two letters stored on that receipt, shown in capitals. A longer value written before that rule is shown as stored. Below 800px the table is hidden and the same fields render as cards, with the same labels.

The server returns those fields. It does not send item prices. A role without `can_view_financials` has those price fields removed before the response is built, including prices nested on the item.

A line with no item shows Link item in the SKU cell, a blank item name, the search text, and the putaway bin. That row is tinted so it stands out from posted receipts. Link item opens the same item finder as a SKU that is already filled, and the finder starts on the stored search so a pending line opens ready to match. The whole SKU cell takes that click. Choosing an item asks before it posts that quantity into the bin already stored, through the same `edit_receipt` path as any other first link. Search stays its own cell and still saves on its own. Click a value to correct it in the cell. The same fields are editable on a phone. Date, project, incoming bin, system, system qty, search, and comment save as soon as the cell closes. A correction keeps the stored search text when that cell is left alone. On a line that still has no item, search, quantity, comment, and the putaway bin can be changed without choosing an item and without moving stock. Clearing the search on that line is refused. The putaway cell edits the bin code. The location shown beside it is the bin's location at the time of that change. On a line that already has an item, changing the putaway bin asks first. Confirming it takes that quantity out of the old bin and puts it in the new one, and the row shows the new bin. A code that is not a bin, a bin that does not exist, or a bin that has quantity and no open cycle is refused with the same error as a new receipt.

SKU uses the same item search as the receiving line. Choosing a different item fills the item name immediately, so the row does not keep the previous name next to the new SKU. Search stays the text already stored on the receipt. It does not become the new SKU, or the text typed in the SKU cell. On a posted line, qty, a different item, or a different putaway bin still asks for confirmation before the save. That confirmation posts a `receipt_adjustment` and moves `bin_contents` through `adjust_bin_cycle_qty`. A putaway change posts one adjustment out of the cycle the quantity sits on and one into the destination bin. An empty destination opens a cycle the same way a new receipt does. The adjustment cannot take a bin below 0. The original receive row stays on the cycle where it was posted. The correction stores the destination cycle, so a later quantity or SKU change adjusts the new bin. Linking an item onto a line that has none asks first, and the question names the quantity and the bin already stored. Confirming that link posts the quantity into that bin once, the same way a normal receive does, including Cleaned or Wiped when the new taxonomy asks for a flag. A second link, or a later change of SKU, is an adjustment of the quantity already posted. It does not receive the line again. The Comment cell shows a status word in front of the stored note, for reading only: `cleaned` or `Dirty` on a CPU, and `Wiped` or `Pending Wipe` on a drive. Those words come from the flags. They are not stored in the comment, and editing the comment changes only the note. Recent entries has no Cleaned or Wiped control. A flag that was never set shows no word. Choosing a different item still resets that flag for the new taxonomy, and still asks for confirmation. Initials stay the letters stored on the receipt. The person making the correction is recorded on `stock_event_edits`, as their signed-in initials, or `OP` when sign-in is off. Header corrections and a pending bin change do not rewrite the ledger row. Each of those saves writes `stock_event_edits` with who, when, and the old and new values. The row then shows the corrected values. The first link is the exception: it fills `item_id`, `cycle_id`, the bin, and the prep flags on the pending ledger row so later adjustments can find the cycle. The date stays the date, with no edited mark beside it.

Detail, Summary, and Export CSV sit on that same card, for the project in the header. A blank project is the receipts with no project, the same set as the table. Detail and Summary are a switch. Detail is the default and shows only the Recent entries table. Summary shows only the summary table. Export CSV stays on the card in either view and saves every receipt line for the project, newest first, including the older pages. The columns match Recent entries, and Cleaned and Wiped are their own columns (`yes`, `no`, or blank). The comment in the file is the stored note. The status word Recent entries shows in front of that note stays on screen, including `Dirty` for a CPU that is not cleaned. Summary is one row per SKU, quantities added together, sorted by item name. Item is the item name when a SKU is linked, and the stored search when the line is still pending. A blank SKU still means no item is linked. Putaway on that table is the quantity in each bin, `(x14)10002-C | (x8)10037`, in bin order. Qty and Lines stay the totals. Lines with no item stay in the report. They are grouped by the exact search text and listed after the SKUs, with a blank SKU, the search in Item, the same putaway breakdown, and the status Pending item. A blank search is one Pending item row. Download summary CSV saves that table. Both files are UTF-8 CSV with a byte order mark. A cell that starts with `=`, `+`, `-`, or `@` is prefixed with an apostrophe. On iPhone and iPad the download is a normal form post so Safari saves the file. Open that CSV in Google Sheets. Creating a spreadsheet in Drive stays on the items export, which already has the Google sign-in for that button.

Apply `supabase/migrations/20261023070123_receipt_edits.sql` before corrections. It is additive. Row level security is on, and the table and functions are granted to `service_role` only. It has not been applied.

## Scanning a line

The SKU field splits the text on spaces and searches the longest token first. When two tokens are the same length, the one with both letters and digits is first. `KR M393A8G40BB4-CWE 2349` searches `M393A8G40BB4-CWE`, then `2349`, then `KR`. The line under the field says which token was used. If that token misses, the next token is tried. A token uses the same search as the items page: SKU, name, description, model, part number, OEM name, OEM part number, product URL, attribute value, manufacturer, manufacturer alias, and eBay item id. `VK000960GZCNF` finds SKU 107068, whose model is that value. Those fields also match when the query and the stored text contain each other after every character that is not a letter or digit is removed, so `MCX-516A-CDAT` finds `CARD\NIC\E30\100G_2Q\LP-FH\MCX516A-CDAT`. A digits-only attribute, such as cache `96.0`, does not match by sitting inside a longer part number. That rule waits on `supabase/migrations/20261026004000_item_alnum_attribute_reverse.sql`, which is not applied. Until it is applied by hand, that fragment can still match. That extra match waits on `supabase/migrations/20261025230000_item_alnum_search.sql`. Until it is applied, search keeps the contains match on those same fields. One hit still selects itself. The typed text stays in Search.

The full scan is stored on `stock_events.scan_raw` only when the search tried more than one token. A single typed SKU, name, or description is not a scan. When the comment is blank, that multi-token scan is stored as the comment so the country of origin and the date code stay on the line. Apply `supabase/migrations/20261023070124_receipt_scan_raw.sql` for the column. It is additive and has not been applied. Until it is applied, a save still keeps the scan in the comment when that field was blank.

The text the operator typed to find the item is stored on `stock_events.search_query`, including a one-token search. It is not copied into the comment. Opening the receipt shows that text in Search, and a correction writes it on the receipt edit. Apply `supabase/migrations/20261025195000_receipt_search_query.sql` by hand after `supabase/migrations/20261025174500_receiving_line_checks.sql`. It is additive. It adds `search_query`, a fifteen-argument `receive_into_bin`, and a fourteen-argument `edit_receipt`. The older signatures stay. `receipt_lines` gains the search text at the end. Row level security is unchanged, and the new functions are granted to `service_role` only. It has not been applied. Until it is applied, a save still receives the line and the search text is not stored.

Country of origin and date code are not their own columns yet. A later migration can add nullable `country_of_origin` and `date_code` on `stock_events` and fill them on insert from the tokens that were not the search hit: a two-letter token as the country, and a four-digit token as the YYWW date code, only when that reading is unambiguous. `scan_raw` stays, so older lines can be read back without rewriting the ledger. Those values belong on the receipt, not on the item, because the same part ships under many date codes.

## Importing a list

Download template on this page saves `receiving-template.xlsx`. Download CSV saves the same columns as `receiving-template.csv`. The header row is the ITS field names. One sample row follows it. The workbook also has an Instructions sheet. Open either file in Google Sheets.

Fill one row per receipt. `qty` and `bin` are required. The bin is a code that already exists (`10059-C`). Import does not create bins. `sku` is an exact item SKU. Leave SKU blank and fill `search` to store a pending line that does not move stock. A row with no `purchase_order` is consigned and needs `vendor`, the vendor's display name. A purchase order number such as `PO6304` supplies the vendor and is not consigned. Blank vendor, purchase order, project, receiving date, incoming bin, originating system, and system qty use the receipt header on the page.

`cleaned` is for a CPU and `wiped` is for an SSD or HDD. Blank, `no`, or `yes`. Blank is no, which is the unchecked box. Other items ignore the flag. `serial` is optional. Several serials can share one cell, separated by a semicolon, a pipe, or a new line, at most one per piece. `country_of_origin` is a 2- or 3-letter code stored on those stock units. With no serial, one stock unit is recorded with that country. Fewer serials than the quantity leaves the rest as quantity only.

Choose the filled file, or paste rows. Headers that match the template, or the receipt export (`Item Qty`, `Putaway`, `PO`, `COO`, and the rest), are mapped automatically. Anything else can be remapped before continuing. The preview lists each row as OK or Error. Nothing is written while a row has an error. Import posts every OK row through `receive_into_bin`, the same path as Save receipt, in one transaction. A failure while posting rolls the batch back.

Data management links here. The import logic is only on this page.

Apply `supabase/migrations/20261029040000_receiving_import.sql` by hand after `supabase/migrations/20261027233000_consigned_receive.sql`. It is additive. It adds `import_receiving_rows` and does not change `receive_into_bin`. Row level security is unchanged. The function is granted to `service_role` only. It has not been applied. Until it is applied, the preview says so and nothing is posted.

## Migrations

Apply `supabase/migrations/20261023055637_receiving_form.sql`, then `supabase/migrations/20261023061105_receive_request_id.sql`. The first one adds the receipt columns and the ten-argument `receive_into_bin`. It also leaves the eight-argument function in place: that signature stores today's date in America/Los_Angeles and a blank originating quantity, then calls the ten-argument function. The live site still uses the eight-argument signature, so dropping it before this branch is merged would stop receiving. A later migration can drop that wrapper after the new form is the only caller. The second migration stores the client request id on the new line. Receipt rows cannot be updated, so the id is written on the insert.

Apply `supabase/migrations/20261025174500_receiving_line_checks.sql` by hand before Cleaned, Wiped, and the Putaway column are stored. It is additive. It adds `stock_events.cleaned` and `stock_events.wiped`, a fourteen-argument `receive_into_bin`, and a thirteen-argument `edit_receipt`. The older signatures stay. `receipt_lines` gains the flags, the taxonomy codes, the bin, and the location. Row level security is unchanged, and the new function is granted to `service_role` only. It has not been applied.

Apply `supabase/migrations/20261025195000_receipt_search_query.sql` by hand after that migration before the receiving search text is stored. It is additive and has not been applied.

Apply `supabase/migrations/20261026021000_receipt_pending_item.sql` by hand after the search migration before a line can be saved without an item. It is additive. It relaxes `stock_events_receive_check` so a `receive_into_bin` row may have both `item_id` and `cycle_id` null when `search_query` is set. It replaces the fifteen-argument `receive_into_bin` so a null item stores the line and does not call `adjust_bin_cycle_qty`. It adds a fifteen-argument `edit_receipt` whose last argument is the putaway bin. The fourteen-argument edit function stays and forwards to it, passing a null bin so the stored bin is kept. The first item on a pending line posts the quantity once and fills `item_id` and `cycle_id` on that row. A later item or quantity change still posts `receipt_adjustment`. `receipt_lines` shows a blank SKU until that link, and it prefers a putaway bin stored on a pending correction. Row level security is unchanged. The new function is granted to `service_role` only. It has not been applied. Until it is applied, saving without an item is refused and no placeholder SKU is created.

Apply `supabase/migrations/20261026201500_receipt_putaway_bin.sql` by hand after that migration before a posted line can change its putaway bin. It is additive. It replaces the fifteen-argument `edit_receipt` so a putaway change moves that quantity from the old bin to the new one. The fourteen-argument edit function stays and still keeps the stored bin. Row level security is unchanged. The function is granted to `service_role` only. It has not been applied. Until it is applied, a posted putaway change is refused.

Apply `supabase/migrations/20261027230000_stock_units.sql`, then `supabase/migrations/20261027233000_consigned_receive.sql`, by hand on project `fxsbpreasbdalwthyzvk` before receiving will post. The second one requires a vendor on every receipt that has no purchase order and stores that receipt as consigned. Until it is applied, the receiving screen refuses the save instead of posting a receipt with no vendor.

Apply `supabase/migrations/20261029040000_receiving_import.sql` by hand after the consigned receive migration before a filled sheet can be imported. It is additive and has not been applied.
