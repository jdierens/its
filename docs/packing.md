# Packing

Warehouse → Packing lists sales orders whose pick is finished, orders already being packed, and shipped orders whose pick is finished and whose pack is still empty. Opening an order sets the sales order to packing. Finish sets that order to packed. A correction that leaves the pack incomplete opens it again. Freight, fees, services, and any line that was not picked stay off the sheet. That includes service item 4343 (`SER\FREIGHT-OUT`).

The sheet is one row per package. Add a row and choose a box or a pallet from the packaging list, or create a type on that row. A box has a fixed length, width, and height in inches. A pallet copies the base length and width, and the operator enters the height. The list starts with a small box, a medium box, a large box, and a standard pallet. The trash icon on a packaging type hides that type. Packages already created from it keep the inches they were given.

Enter the weight on the package row. Add contents from that same row. Item is always available: choose a SKU that still has unpacked quantity and enter how many. That new quantity starts at 1, not the full remainder. Serial is available only when the pick recorded serial numbers. A serial is resolved to the item on that pick. It does not create a SKU. The row is complete when the package, the weight, and the contents are set. It stays editable. Duplicate copies a complete package into the next one: same type, size, weight, and item quantities, when that much is still unpacked. Serials already in the source stay there. The copy uses the next unpacked serials of that item when the pick has them.

Above the packages, the overview lists each picked SKU, the name, the quantity picked, what is still unpacked, and one column per package with the quantity of that SKU in that package. Remaining sits between the picked quantity and those package columns. The table follows the packages as they change.

A packed item reads as `1 × 106703`. The quantity and the item on that row can be changed without deleting the package. The quantity field starts at what is already in the package. It can go up while unpacked quantity of that SKU remains, and it can go down to 1. The trash control still takes that quantity out. The item can be replaced with another picked line that still has unpacked quantity. When that line is already in the package, the saved quantity is added to it. Serials stay on the item the pick recorded. Changing the item does not move them.

The trash control on a package row removes that package. The trash control on a content chip takes that quantity, or that serial, back out. Picked lines are not a second table of bin icons. A line can still be split across packages.

Finish packing stays off until every picked quantity is in a package and every package has a weight. A pallet also needs its height. Finish is the save icon at the top of the sheet. The hint says Unsaved changes while finish can run, Saving… while it runs, and All changes saved otherwise. The icon stays grey until finish can run. Ctrl or Cmd+S finishes when the icon is enabled.

Finish packing sets an order that is still packing to packed and stores `packed_at`. Warehouse → Shipping lists those orders. Carrier labels and rate shopping are not on this screen.

Finish does not lock the sheet. Packages, weights, heights, and quantities can still be corrected on a packed order and on a shipped or partially shipped order. The sheet says so. A correction that leaves a line short, a package without a weight, or a pallet without a height reopens packing. On a packed order that means the status goes back to packing and `packed_at` is cleared, so Warehouse → Shipping drops it until Finish is used again. On a shipped or partially shipped order the status, the ship date, and the shipment rows stay as they are, and only `packed_at` is cleared. A correction that stays complete leaves the pack finished. Finish checks completeness again after a reopen. Cancelled, invoiced, and closed stay closed. Apply `supabase/migrations/20261106010000_pack_edit_after_finish.sql` by hand after `supabase/migrations/20261104183000_pick_shipped_orders.sql`. Deploying does not run it. Until that file is applied, a finished pack still refuses the save and the sheet names the file.

An order that already shipped without this step stays shipped. That includes a historic eBay order whose status is shipped, whose ship date and shipment rows are already stored, and whose `packed_at` is still empty. The pack sheet can add packages, assign the picked quantity, and store weights. Finish stores `packed_at` and leaves the status, the ship date, and the shipment rows as they are. A later correction keeps that status, that ship date, and those shipment rows. Cancelled, invoiced, and closed orders stay closed. Warehouse → Packing lists that order once the pick is finished and `packed_at` is still empty. The sales order stage control opens the sheet before that, and the sheet says to finish the pick first. The pack stage icon stays yellow until a package exists or `packed_at` is set. That rule is unchanged.

The fulfilled SKU is the one that was picked. A replacement shows that SKU, with the planned SKU under it. On the package row a quantity reads as `8 × 106683`. Where a label names both the quantity and the package, it reads as `8 in Box 1`.

The header beside the sales order number is the same stage control as the sales order and the pick sheet. It goes back to those pages. On an order that has not shipped, packing in that control stays off until the pick is finished.
